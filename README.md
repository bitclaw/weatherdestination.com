# warpkit: TanStack Start SaaS Starter

**Auth + billing + per-user SQLite + file uploads + credits metering + AI chat + more: ship features, not infrastructure.**

A production-ready B2C SaaS starter template built with:

- **TanStack Start**: full-stack React with server functions and file-based routing
- **better-auth**: OTP / magic-link / social OAuth (Google, GitHub, GitLab, Bitbucket)
- **Stripe**: subscriptions, one-time purchases, customer portal, webhook handling, credits top-up
- **Drizzle ORM**: type-safe SQL with native bun:sqlite (shared metadata DB)
- **Per-user SQLite**: each user gets their own isolated database via `bun:sqlite`
- **Background jobs**: SQLite-backed queue (`@bitclaw/jobs`) surviving server restarts
- **File uploads**: S3 presigned POST/GET with per-user SQLite metadata
- **AI Chat**: SSE-streaming chat via OpenRouter, per-user conversation history
- **Feature flags**: runtime DB-backed toggles with admin UI
- **In-app notifications**: per-user notification bell
- **Domain events**: in-process typed event bus
- **Blog**: markdown posts with content-collections
- **Tailwind CSS v4**: with dark mode and design tokens
- **React Compiler**: active — no manual `useMemo`/`useCallback` needed

## Quick Start

### 1. Clone and bootstrap

```bash
git clone <repo>
cd warpkit
make init
```

`make init` copies `.env.example` to `.env`, generates `BETTER_AUTH_SECRET`, installs dependencies, and runs migrations. Safe to re-run.

### 2. Configure

Edit `config.ts` at the project root:

```ts
export const config = {
  appName: 'My App',          // shown in UI and emails
  domainName: 'myapp.com',    // used in SEO and absolute URLs
  stripe: {
    plans: [{
      name: 'Pro',
      priceId: 'price_xxx',   // from your Stripe dashboard
      price: 9,
      // ...
    }]
  },
  // ...
}
```

### 3. Set environment variables

Fill in `.env` with your real keys:

| Variable | Where to get it |
|---|---|
| `STRIPE_SECRET_KEY` | Stripe Dashboard |
| `STRIPE_WEBHOOK_SECRET` | Stripe CLI or Dashboard webhook endpoint |
| `RESEND_API_KEY` | Resend |

(`BETTER_AUTH_SECRET` was generated by `make init`.)

### 4. Start the dev server

```bash
make dev
```

Visit http://localhost:3000.

> To start with a clean git history: `rm -rf .git && git init && git add -A && git commit -m "init"`

## Architecture

### Two-Database Pattern

```
data/
  meta.db              <- shared metadata (Drizzle ORM)
    users              <- hasAccess: boolean set by Stripe webhook
    sessions
    accounts
    subscriptions
    leads

  users/
    {userId}/
      user.db          <- per-user domain data (raw bun:sqlite)
        notes           <- replace with your domain tables
```

**Metadata store** (`src/lib/db/`): Drizzle ORM, holds auth + billing + feature flags data.

**User store** (`src/lib/db/user-db.ts`): raw bun:sqlite, isolated per user. Migrations run lazily on first open.

### Billing

One boolean: `hasAccess` on the `users` table. Set to `true` by the Stripe webhook when a subscription starts, `false` when it cancels or payment fails.

Gate Pro features with `<UpgradeGate>` or check `hasAccess` from route context:

```tsx
const { hasAccess } = Route.useRouteContext() as AppRouteContext;

{hasAccess ? <ProFeature /> : <UpgradePrompt />}
```

### Auth

OTP, magic-link, and social OAuth via better-auth. Users enter their email, receive a code, and land on `/dashboard`. Multi-session lets users stay signed in on multiple devices.

## Customizing Your App

### Add a database table

This is the core pattern for adding any new feature:

1. **Create a migration** at `src/lib/db/migrations/YYYYMMDD_HHMMSS_description.ts`:

```ts
import type { Database } from 'bun:sqlite';

export const migration = {
  id: '011_create_widgets',
  run: (db: Database) => {
    db.run(`CREATE TABLE IF NOT EXISTS widgets (...)`);
  }
};
```

2. **Import and register** it in `src/lib/db/user-migrations.ts`:

```ts
import { migration as m011 } from './migrations/20260702_220000_create_widgets';
// ...
USER_MIGRATIONS: [..., m009, m011]
```

3. **Write server functions** in `src/features/widgets/server/`:

```ts
export const getWidgets = createServerFn().handler(async () => {
  const user = await requireUser();
  if (!user) return err(ERROR_CODES.UNAUTHORIZED, 'Not authenticated');
  const db = getUserDb(user.id);
  const widgets = db.query('SELECT * FROM widgets ORDER BY created_at DESC').all();
  return ok(widgets);
});
```

4. **Create a barrel** `src/features/widgets/index.ts` exporting the public API.
5. **Add a route** at `src/routes/_app.dashboard.widgets.tsx`.
6. Run `bun run generate` to update the route tree.

The `notes` feature in `src/features/notes/` is the canonical reference implementation for simple CRUD.

### Stripe setup

1. Create a product and price in the Stripe Dashboard
2. Copy the `priceId` into `config.ts`
3. Set up a webhook endpoint pointing to `https://yourdomain.com/api/v1/stripe-webhook`
4. Subscribe to: `checkout.session.completed`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.payment_failed`

For local testing: `stripe listen --forward-to localhost:3000/api/v1/stripe-webhook`

### Blog

Write posts in `src/content/blog/` as `.md` files:

```markdown
---
title: "Your Post Title"
description: "A short description for SEO."
published: "2025-01-15"
authors: ["Your Name"]
---

# Your post content here
```

### Gating e2e without a CI runner (optional)

`.github/workflows/ci.yml` runs `make ci` (typecheck, build, lint, unit tests) on every push — cheap, zero setup, works the moment you push a fork. e2e tests ship as source but are **not** part of that workflow: most forks won't have `.env.e2e` secrets or want browser binaries slowing down every push.

If you want e2e enforced without paying for a slower/more expensive CI job, [gh-signoff](https://github.com/basecamp/gh-signoff) runs it locally and stamps a commit status via the GitHub API instead:

```bash
# One-time setup
gh extension install basecamp/gh-signoff

# Before pushing a branch that touches anything e2e-relevant
make signoff
```

To require it for merges, a repo admin runs `gh signoff install e2e` once. That requires a status named `signoff/e2e` (the CLI prefixes whatever name you give it) on the default branch — if you're wiring branch protection by hand instead of via `gh signoff install`, search for `signoff/e2e`, not `e2e`. This is trust-based, not enforced by a runner — nothing stops signing off without actually running tests — so it's a fit for a small/trusted-committer repo, not a substitute for `ci.yml`'s automated check on outside contributions.

The signoff itself lives on GitHub's servers, not in your repo — `gh signoff e2e` posts a commit status (no Git note, no commit message change, no signature), a *different* API from the check-run `ci.yml` creates. On a commit pushed straight to the default branch, GitHub folds both into one small checkmark button (e.g. "2/2") on the commit page — not obvious which two things that is. On a **pull request**, the same two checks show up separately and much more visibly: each listed by name in the PR's checks list, with its own pass/fail status, at the bottom of the Conversation tab. If you want signoff to actually feel like a gate (not a hidden checkmark), route changes through PRs rather than pushing straight to the protected branch.

### Multi-user load test (1000 unique per-user databases)

The single-user flow above puts all concurrent workers on one per-user SQLite DB, which stays hot in OS page cache. That's best-case, not representative. To test realistic multi-tenant pressure, seed 1000 distinct users first:

```bash
make prod.cluster   # terminal 1: production build + clustered server

make loadtest.seed  # terminal 2: creates 1000 users + per-user DBs, writes data/loadtest-sessions.json
bun run test:load --full
```

`make loadtest.seed` uses `.env` (your dev database). It inserts 1000 `loadtest-N@test.loadtest.internal` users into the shared DB and creates 1000 per-user SQLite files under `USER_DATA_DIR`. The script is idempotent — safe to re-run. `data/loadtest-sessions.json` is gitignored (contains signed session tokens).

The `.env.test` database and `make ci` / `bun test` are not affected.

### Load testing against a remote server

Running the load generator and the server on the same machine means they compete for CPU and memory. For credible numbers, run the server on a remote host (e.g. Hetzner) and the load generator locally.

**On the remote server:**

```bash
# 1. Deploy warpkit and start the production cluster
make prod.cluster

# 2. Seed 1000 loadtest users (uses the server's DB and BETTER_AUTH_SECRET)
make loadtest.seed

# 3. Copy the signed session cookies to your local machine
scp user@<server-ip>:~/warpkit/data/loadtest-sessions.json data/loadtest-sessions.json
```

The session cookies are signed with the server's `BETTER_AUTH_SECRET` and reference users in the server's DB — they must be generated on the server, not locally.

**On your local machine:**

```bash
LOADTEST_BASE_URL=http://<server-ip>:3000 bun run test:load --full
```

`LOADTEST_BASE_URL` overrides the default `http://localhost:3000`. Make sure port 3000 is open in the server's firewall. For benchmarking, hit the origin directly rather than through a reverse proxy so TLS overhead doesn't skew latency numbers.
